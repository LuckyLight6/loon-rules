# 规则怎样自动更新

更新任务计划每天北京时间 **11:37 和 23:37** 运行，也可以在 [Scheduled rule maintenance](https://github.com/LuckyLight6/loon-rules/actions/workflows/schedule.yml) 选择 `readme` 分支手动触发。它下载公开资料，生成候选，检查归属与首条命中，再从同一份结果生成各客户端格式，通过后提交规则、客户端成品、插件和维护状态。读取失败或关键检查失败时，已发布版本继续可用。

两次计划给漏触发留一次补充机会；[GitHub 的定时任务](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)可能延迟或被丢弃，并不保证准点。它在 GitHub 上更新文件，不在 Loon 客户端运行脚本或测速；客户端何时刷新订阅由自己的设置决定。

仓库首页使用 `readme` 分支，代码和规则在 `main`。默认分支保留一个可直接运行的定时任务：先检出 `main`，再调用其中的共用维护组件。手动维护入口也调用同一组件，业务代码只维护一份；任务只更新 `main`，订阅地址中的分支不变。定时与手动更新共用同一并发组，避免同时向规则分支提交。

GitHub API 请求使用 Actions 自带的临时令牌，减少匿名请求限额的影响。令牌只发给 `api.github.com` 的标准 HTTPS 端口，带令牌的请求不跟随重定向；其他公开来源不使用它。

Apple 软件版本和服务配置使用 Apple 的证书链。Linux 工作流从 [Apple 官方 PKI](https://www.apple.com/certificateauthority/)下载 Apple Root CA 与 G3 根证书，与系统 CA 合并成临时证书包，供来源下载使用；HTTPS 的证书与主机名校验保持开启。

运行摘要留在 Actions，本地生成的摘要在 `build/verification.md`，不进入版本管理。下一轮仍要使用的采用依据、撤回观察与来源基线保存在 [data/maintenance-state.json](../data/maintenance-state.json)；这是更新数据，不是工作日志。

## 新端点按什么条件补入

| 资料给出了什么 | 怎样使用 |
|---|---|
| 官方业务表、SDK 默认地址、API 或下载字段 | 按明确用途提取。字段出现符合条件的新主机，细分、合集和命中用例一起更新 |
| 官方产品目录、地区表或客户端版本目录 | 跟随目录读取相应文档，不逐个维护地区、版本、机型或 API ID |
| 超出既有范围的新根域 | 官方明确用途可证明其列出的范围；普通候选至少要有两个独立来源家族支持 |
| 服务的 CNAME 链 | 核对原服务与允许的厂商别名，只收符合关系的名称。共享边缘服务器与解析 IP 不直接当作业务规则 |
| 注册组织当前持有的 ASN 列表 | 核对组织 ID、名称及完整活动列表后跟随成员变化；组织身份是声明，ASN 编号从记录取得 |
| 只有一个社区来源或用途不明的名称 | 保留已有结果，记录差异；不能凭名称相似决定代理、直连或拒绝 |

镜像、转存和共同上游不重复计票。精确主机的证据不能扩大成整个父域；共享云、其他产品的主机和已有明确排除仍会拦住候选。来源失效时，已采用范围和此前确认的必需入口继续保留，不把故障时间算作撤回依据。

例如 Apple 商店、音乐和视频从同一份公开配置读取各自的 API 字段；Google 登录结合官方地区模板与注册域清单；GitHub 读取 Meta API 的网站、软件包和 Actions 域名。读取的是业务字段，不是页面中的全部链接。各文件头的 `source` 列出资料，动态展开的逐份文档和采用依据记在维护状态里。

用途资料已给出精确主机时，也用这些字段核对社区表，不重复维护一份名字筛选。Kiro 的模型服务按官方用途列跟随地区变化；Together 的 API 默认值同时读取两代官方 Python SDK。官网资讯链接、地区隐私文档和已核实的网站跳转也可补充入口，各自保留品牌、命名空间与用途检查。

OpenAI 的官方网络文章也直接参加生成和核对：自有登录、对话、文件与静态资源入口归 OpenAI；文章同时列出的 WorkOS、支付、客服和验证码等共享服务单独说明，不能据此把它们整段归给 OpenAI。官方清单出现无法归属的新范围时停止发布，保留上一版。

## 从来源消失后怎样处理

不同资料的含义不同，不能统一“这次没出现就删除”：

- **完整服务清单：** 先合并所有来源与仍公开的 API 版本。单个主机从所有清单消失后，间隔至少 20 小时再次确认才撤回；其他新增项不重置它的观察。超过三天未连续确认、主机重现或来源范围改变时，重新观察
- **已核对的社区表：** 声明允许撤回的表，也要两次相隔至少 20 小时确认；一次最多撤回原表条数的 5%，不足 20 条的小表允许撤回一条。大幅减少时保留基线
- **发布文件的下载主机：** 保存公开版本与首次采用依据。新版本换 CDN 不代表其他版本已经不用原主机，因此不套用上述短期撤回条件
- **局部客户端配置：** 某个版本、地区或用途的配置不能代表全部服务。只保留此前来源明确证明、已经发布且仍符合当前用途的精确主机，不借历史记录引入新范围；第三方命名空间也不能自动沿用
- **CNAME 别名变化：** 查询不完整时，仅沿用已发布且仍符合用途的关系。查询成功但换了区域节点时，已发布、名称明确包含原厂商服务标识的精确别名可以作为历史分发入口保留；独立第三方租户不能这样沿用。两种情况分别记录，不把正常轮换说成查询故障
- **组织持有的 ASN 集合：** 对已核实的产品网络运营者，完整组织记录决定当前成员；不再登记给它的 ASN 撤出，新成员自动加入。组织身份变化、空列表、截断、保留编号或成员格式错误时停止更新。域名和其他网络的覆盖检查继续执行

已明确排除或改归其他产品的范围不会因历史记录继续留下。完整清单和配置中的明确主机，即使在正文里压缩进后缀规则，也继续生成逐主机的命中用例。

## 归属、补充与优先级一起计算

产品只维护一份业务声明；合集从成员生成。客户端导出只转换语法，不再决定归属；无法等价转换的整组明确列为不支持，已发布的可用订阅发生兼容退化时停止更新，保留上一版。不同合集可以提供互斥用法，例如 Apple 完整合集与日常直连／海外拆分。生成器从共同成员判断哪些选择不能叠加，检查所有合法组合；目录仍列出全部可选表。目录、文件编号和测试使用同一个执行顺序，不能分别维护三套名单。

常规细分与补充之间不允许完全相同的规则；后置专项被前面的规则整条盖住时也会报错。前置的具体服务主机与后置的共用父域可以有包含关系：专项先匹配，父域仍需识别其他请求。补充表会扣除已有专项完整接住的范围，并保存扣除依据，下轮从来源重新计算，避免产品拆分后永久丢失覆盖。

Bilibili 国际版的部分专用主机就在中国站使用的父域下，因此不能要求两表完全没有包含关系。国际版业务清单中的具体 API 和视频主机先精确匹配，中国站与共用父域随后处理；中国站正例、国际版正例和不应混入的海外 CDN 分别检查。官网实际引用的素材另作完整性核对，国内、国际版两个合集也按同样顺序验收。

海外补充保留两份用途：8210 其他影音、8220 其他网站与受限站点。国内补充只有一套：8600 合集，或其成员 8610 域名、8620 网段、8630 GeoIP。上游比对输入存在 `source-components` 中，不再分别输出兼容订阅。

8220 采用的三份海外与 GFW 来源优先于宽泛国内补充：来源明确列为海外的范围，不因国内大表也收录就失去代理规则。具体国内产品仍在 8220 前面；共享云和公共后缀继续排除。每轮从来源重新计算，并让国内补充移除已经被前面完整覆盖的条目。以后加入的输入要单独声明来源优先权，不能默认套用。

业务细分也要保住整段覆盖。`separates` 声明从哪个同类公共范围拆出服务；生成器核对共同来源、新表的完整覆盖和唯一归属。只补根主机、让请求落兜底，或没有共同来源，都不能作为成功拆分。这用于 Find My、设备登记和反馈诊断等用途，避免每次拆表都加一组永久域名豁免。

独立服务清单同时核对完整域名范围和实际第一条命中。已选产品的范围被无关产品或地区兜底接住，同样算失败；不能用“总有规则能匹配”代替正确归属。已声明清单的新增范围未归属、清单格式损坏或无法读取时，都不能只留下待审提示后继续发布。通配符按完整范围核对，合集和细分按替换关系检查。

已确认用途的完整产品来源还启用 `require-domain-closure`，检查筛选前的全部域名范围。新名称被筛掉、落入补充或被无关产品接走，都会停止发布；共享与排除必须有依据。其余混合参考表继续列出筛选外差异，不把“已选范围没有遗漏”写成整份来源已校准。Actions 摘要分别列出两类来源。

Apple 通用补充跟随 Sukka 的整份 Apple 自有域名表，不再另列一份根域白名单；进程与 IP 规则不参与。Apple 细分先匹配，已由细分完整承接的条目从补充中扣除。采用整份公司来源必须声明独立完整性清单，新增范围仍受共享平台和过宽匹配检查约束。

公司域名表不一定适合作为应用端点全集。Instagram 和 Meta 的来源含有品牌拼写变体、买粉和周边站点，不能整表导入产品规则；这里按已确认的业务域筛选，Instagram 短链另跟随维护中的产品表。Meta AI 的专用内容域归 AI，社交共用服务留在 Meta 表中。用途边界仍是人工声明，来源在这些范围内新增的主机随更新补入。

7800 扩展广告采用网站范围保护：与已列正常网站同一范围，或会整体覆盖更具体正常入口的拒绝规则退出广告表，并记录归属。专用广告子域仍可单独拦截，不因网站父域在普通表中就全部放行。网站规则继续保留，开关广告都不丢失正常选路。

## 广告和国内地址各自怎样核对

**0220 常规广告**先保护来源明确的必需登录、API 和文件主机。新增域名要由原规则来源、EasyList 或 EasyPrivacy、AdGuard DNS 共同支持整域拦截；已审域名须有原来源支持，或仍通过两类过滤资料的整域核验。无条件放行例外可以撤销拦截，某个网页或路径的放行不扩大成全局放行。已有 IP 也重新检查原来源，单个广告表新加的 IP 不自动采用；一次范围增减超过 5% 时保留基线。

**7800 扩展广告**对整份候选都要求上述整域交叉核验，并考虑可识别的放行例外。按路径、脚本或第三方请求生效的拦截不扩大为拒绝整站。这些清单可能有共同来源，不当作独立证据计票。

**8620 国内网段**每轮比较完整地址空间，取上游、APNIC 中国分配记录与运营商路由清单共同支持的范围，部分支持时拆开保留。一次地址空间增减超过 5% 时保留上一版。APNIC 主入口不可用时尝试官方备用入口，同时核对机构、记录数、地址族及七天内的日期；两个入口只算一个来源。

分配地和运营商归属不能证明服务器就在大陆。8620 是补充判断，域名专项先匹配；8630 还取决于设备上的 GeoIP 数据库。[APNIC 对地理位置数据的说明](https://blog.apnic.net/2024/12/05/how-to-boost-geolocation-accuracy-with-geofeed/)

## 哪些仍由人决定

部分 AI API 从 [models.dev 的提供商目录](https://models.dev/api.json)读取。它是维护中的客户端配置资料：按提供商 ID 选择 `api` 字段，产品官网范围只取对应 `doc` 地址所属的已确认产品域，不扫描全部链接。小米 MiMo 等分地区计划按目录中的不同记录分开；共用 API 保留共用说明，不能从同一个主机推断账户地区。提供商目录不是各厂商的官方网络端点全集。

产品和用途边界、共享基础设施、已知例外与测试样本仍要有人负责。`include`、`literal_ips`、`dns_required` 是固定声明；`roots`、`exact` 等名称筛选同样是人工条件，换个字段存放不算自动发现。维护状态分别统计固定声明、精确筛选与来源提取，方便继续减少固定端点。

能读业务字段的地方，优先读取字段。Docker 的更新、诊断、Scout 和 Offload 按官方用途取主机，表中换主机后自动跟进；同一张表另由完整性检查逐行核对，新用途也会被发现。Auth0 和 Bugsnag 分别归共享供应商，避免把 Docker 的全部依赖都算作 Docker 自有服务

来源中的 IPv4、IPv6、ASN 和进程规则也按类型列入检查记录。进程规则适用的设备单独判断：Loon Mac 已提供进程匹配，iPhone 的公共订阅不直接沿用桌面进程名。[Loon Mac 更新说明](https://nsloon.app/Loon4Mac/changelog.html)

局域网地址和明确的隐私选择可以保留固定声明。能从可靠用途资料读取的业务端点，优先接入来源。未知公司和未知用途无法仅凭计时任务可靠分类；有来源依据的新端点可以自动补入，缺少依据的变化需要维护者判断。

## 从哪里查原因

| 维护状态字段 | 回答的问题 |
|---|---|
| `discovery`、`expanded-inputs` | 采用了什么公开依据，目录展开了哪些文档 |
| `service-inventories`、`config-endpoint-history` | 哪些主机仍在清单、保留观察或按公开历史依据沿用 |
| `cname-alias-evidence` | 哪条原服务与别名关系本轮确认或暂时保留 |
| `public-suffix-state` | 本轮公共后缀表的来源版本与采用版本；缓存返回旧版时沿用较新的已发布版本 |
| `projection-coverage`、`projection-reassignments` | 筛选前的范围有没有漏查，非域名类型有哪些，拆分后由谁完整承接 |
| `assigned-rules`、`subscription-audit` | 补充让出了哪些范围，常规表和可选表怎样重合 |
| `maintenance-audit`、`ip-matching` | 哪些仍是固定项，哪些 IP 规则允许为匹配而解析 |
| `component-rules`、`component-metadata` | 内部比对来源的已核对正文与时间，供下一轮更新使用 |

“筛选外未覆盖”包含历史入口、共享平台和尚无归属依据的名称，不能全部当作应补入的漏项。已选产品范围缺少承接，或要求完整归属的来源出现未处理范围，都会阻止生成。规则检查通过证明本轮已检查范围的归属与顺序，实际连通、DNS、WebRTC 和推送仍需[设备验证](network-testing.md)。
